# B1 premise measurement — v2 vs v1-fork CPU under streaming

Answers one question: does v2 in operation cost significantly more CPU than our
v1 fork under streaming, and does a relevant share of that sit in the **server**
process — the share a worker/process isolation of the AI part (v2 plan point B1)
could move?

Deliverable is a number per process role, plus a Go/No-Go for B1.

## Scripts

| file | what it does |
| --- | --- |
| `b1_common.py` | isolated arm environments, pinned binary copies, prompt, ports |
| `b1_proc.py` | `/proc` introspection: 100 ms sampler over a process tree, per-role CPU/RSS/PSS integration |
| `b1_paired_measure.py` | **primary** — starts the v2 and the v1 TUI side by side and interleaves one stream per arm |
| `b1_tui_measure.py` | single-arm TUI run (what the paired runner drives) |
| `b1_headless_measure.py` | secondary — `serve` + `run --server/--attach` as two separate processes |
| `b1_analyze.py` | turns a result JSON into the report tables |

## Arms

| | client | server | AI process |
| --- | --- | --- | --- |
| v2 | TUI (`opencode --standalone`) | private server child (`serve --stdio`) | none — the model stream runs **in the server process** |
| v1 | TUI (`opencode-v1-bin`) | `serve --shared` child | `__opencode_ai_worker__` pool (children of the server) |

Verified in source: v2 has no `new Worker` / `Bun.spawn` / `child_process` anywhere
under `packages/core/src/session/` and no `__opencode_ai_worker__` in the tree; v1
spawns the worker at `packages/opencode/src/session/llm/ai-process-client.ts:117`.

## Method

- **Isolation.** Each arm gets its own `XDG_CONFIG/DATA/STATE/CACHE_HOME` and an
  isolated config copy. The live installation is never touched: no restarts, no
  kills, no writes to `~/.config/opencode` or `~/.opencode/bin`.
- **Credentials.** `opencode auth export` (read-only) into the isolated store via
  `auth import --server`. `OPENCODE_DISABLE_CHANNEL_DB=1` gives both arms the same
  `opencode.db` — v2 otherwise derives its sqlite file name from the build stamp
  and would start without credentials.
- **Pinned binaries.** The installed v2 binary was rebuilt while this measurement
  ran, so both arms run from frozen copies in `.yesmem/tmp/bin/`; `md5` and the
  version stamp are recorded in every result file.
- **Same conditions.** Same model (`gateway/gd-flash`), same prompt, same terminal
  size (50x200), same working directory — a small scratch git repo, so v2's
  shadow-git snapshot cost does not depend on repository size. The `git` processes
  are measured as their own role.
- **Paired design.** Both TUIs stay up and alternate one stream per arm, so both
  arms see the same host load. Round 0 is a warm-up (v1 builds its worker pool on
  the first stream) and is reported separately.
- **Stream end detection.** The TUI repaints whole frames, so a text marker cannot
  distinguish the current answer from a previous one. Idle output is measurably
  zero (0 bytes/2 s), so the stream window ends at quiescence (3 s without output,
  after an initial burst).
- **Detached servers.** The v1 shared server detaches (ppid 1) and outlives its
  TUI, so a later TUI attaches to it and the server is *not* a child of the TUI.
  The sampler therefore roots at the server process, discovered by scanning
  `/proc/*/environ` for the arm's own `XDG_DATA_HOME`, and adds the TUI as the
  client role. Leftover servers of the same arm are terminated before a run.
- **Host load** is recorded for every window. Absolute percentages under load are
  not portable; the paired ratios are.

## Reproduce

```sh
mkdir -p .yesmem/tmp/{bin,benchdir}
cp ~/.opencode/bin/opencode   .yesmem/tmp/bin/opencode-v2
cp ~/.opencode/bin/opencode-v1-bin .yesmem/tmp/bin/opencode-v1
# config + credential setup: see METHOD in the report; raw artifacts in .yesmem/tmp/

python3 bench/b1_paired_measure.py --rounds 7 --out .yesmem/tmp/b1-paired.json
python3 bench/b1_analyze.py .yesmem/tmp/b1-paired.json
```

Raw result files and the terminal capture live in `.yesmem/tmp/` (git-ignored).

## Results — paired TUI series

7 rounds per arm, interleaved, round 0 is warm-up. 50x200 terminal, model
`gateway/gd-flash`, prompt asks for the integers 1..1500 (~3500 output tokens per
stream). Host load 8.0-10.9, power profile `performance`.

Binaries: v2 `0.0.0-workingv2-202610131858` (md5 `f79b5311…`), v1
`1.18.34-patched.219` (md5 `789ff52c…`).

### CPU, % of one core (median of 6 rounds, warm-up excluded)

| role | v2 | v1 | ratio |
| --- | --- | --- | --- |
| client (TUI) | 17.31 | 6.08 | 2.85 |
| server | 9.55 | 2.23 | 4.29 |
| worker (`__opencode_ai_worker__`) | — | 5.60 | — |
| **total** | **27.95** | **14.26** | **1.96** |

v1 server + worker = 7.83 %, i.e. 1.22x below v2's single server process.

### Idle (20 s windows, both arms up)

| | v2 | v1 |
| --- | --- | --- |
| before the series | 1.35 % | 1.90 % |
| after the series | 1.40 % | 2.20 % |

### CPU per 1000 output tokens (seconds)

| role | v2 | v1 |
| --- | --- | --- |
| client | 0.876 | 0.289 |
| server | 0.479 | 0.103 |
| worker | — | 0.281 |
| **total** | **1.414** | **0.651** |

### Peak PSS during streaming (median, MiB)

| role | v2 | v1 |
| --- | --- | --- |
| client | 271 | 432 |
| server | 201 | 576 |
| worker | — | 79 |
| **total** | **472** | **1087** |

## Headless cross-check (CLI client instead of the TUI)

Same model, same prompt, `serve` + `run --server/--attach` as two separate
processes, 4 valid streams per arm. It exists to separate *architecture* from
*client implementation*.

| role | v2 | v1 |
| --- | --- | --- |
| client (`run` CLI) | 1.41 | 9.62 |
| server | 14.13 | 2.92 |
| worker | — | 11.91 |
| **total** | **15.90** | **24.37** |

Server-side the arms are equal here too: v2 14.13 vs v1 server+worker 14.83.

## Verdict

The premise has two halves; they come out differently.

**1. "v2 costs significantly more CPU than our v1 fork under streaming" — holds
for the TUI, not in general.** With the TUI as client: 27.95 vs 14.26 % of one
core (1.96x), 1.414 vs 0.651 s per 1000 output tokens (2.17x), idle 1.4 vs 2.1 %.
With the CLI `run` as client the ranking *reverses* (v2 15.90 vs v1 24.37).
"v2 is heavier" is therefore a property of the TUI client, not of the core.

**2. "a relevant share of it sits in the server process, which B1 could move" —
does not hold.** Decomposing the TUI gap (12.95 points of one core):

| share | points | % of gap |
| --- | --- | --- |
| client (TUI) | 11.23 | 86.7 |
| server side (v2 server minus v1 server+worker) | 1.72 | 13.3 |

B1 can only touch the server side, i.e. ~13 % of the difference. And the server
side is not where the two arms diverge at all: v2's single server (9.55) is only
1.22x v1's server + worker together (7.83) in the TUI series, and in the headless
cross-check they are equal (14.13 vs 14.83).

**Upper bound for B1.** Moving AI work out of the v2 server can relocate at most
the server's whole stream cost — 9.55 points of one core in the TUI series
(14.13 headless). The AI-attributable part is bounded by what the same work costs
in v1's existing worker: 5.60 points (TUI), 11.91 (headless). Since that work
still has to run somewhere, B1 moves CPU between processes rather than removing
it; it cannot be expected to close a gap that is 87 % client-side.

**Go/No-Go: No-Go for B1 as a CPU lever.** The measured lever is the TUI client
(86.7 % of the gap), not the server.

Caveats on the premise as written: its v1-fork baseline (~3 %) is not
reproducible in this setup — the v1 fork measures 14.26 % (TUI) / 24.37 % (CLI)
of one core under streaming — so the "v2 ~40 % vs v1 ~3 %" framing overstates the
ratio by roughly 6x. Absolute load is modest throughout: even the TUI case is
~28 % of one core on a 16-core host.

## Limits

- The v2 arm runs `--standalone` (private server child) rather than the managed
  background service, because the managed-service registry is not isolatable by
  `XDG_STATE_HOME` and touching the live service was out of bounds.
- The measured symbol-level attribution of the v2 server CPU was **not** done
  (no in-process profile). The server numbers are totals per process.
- Assumed, not verified: the measured v2 binary carries the workingv2 line
  (B3/B4). The stamp says `workingv2`; the exact commit behind a compiled binary
  cannot be read back from it.
