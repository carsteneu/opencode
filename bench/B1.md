# B1 premise measurement — v2 vs v1-fork CPU under streaming

Answers one question: does v2 in operation cost significantly more CPU than our
v1 fork under streaming, and does a relevant share of that sit in the **server**
process — the share a worker/process isolation of the AI part (v2 plan point B1)
could move?

Deliverable is a number per process role, plus a Go/No-Go for B1.

## Scripts

| file | what it does |
| --- | --- |
| `b1_common.py` | isolated arm environments, pinned binary copies, prompt, ports |
| `b1_proc.py` | `/proc` introspection: 100 ms sampler over a process tree, per-role CPU/RSS/PSS integration |
| `b1_paired_measure.py` | **primary** — starts the v2 and the v1 TUI side by side and interleaves one stream per arm |
| `b1_tui_measure.py` | single-arm TUI run (what the paired runner drives) |
| `b1_headless_measure.py` | secondary — `serve` + `run --server/--attach` as two separate processes |
| `b1_analyze.py` | turns a result JSON into the report tables |

## Arms

| | client | server | AI process |
| --- | --- | --- | --- |
| v2 | TUI (`opencode --standalone`) | private server child (`serve --stdio`) | none — the model stream runs **in the server process** |
| v1 | TUI (`opencode-v1-bin`) | `serve --shared` child | `__opencode_ai_worker__` pool (children of the server) |

Verified in source: v2 has no `new Worker` / `Bun.spawn` / `child_process` anywhere
under `packages/core/src/session/` of this branch (this worktree is the v2 line),
and the model stream runs in-process at `packages/core/src/session/runner/step.ts:73`
(`LLMClient.Service`) and `:111` (`llm.stream`). The v1 worker spawn cited below
lives in the *v1* checkout (`/home/chief/projects/opencode`, branch `working`), not
in this tree: `packages/opencode/src/session/llm/ai-process-client.ts:117` returns
`[process.execPath, "__opencode_ai_worker__"]`, pool cap 2 (6 on the shared server),
30 s idle retire, gated to openai-compatible providers with a baseURL — `gateway`
qualifies.

## Method

- **Isolation.** Each arm gets its own `XDG_CONFIG/DATA/STATE/CACHE_HOME` and an
  isolated config copy. The live installation is never touched: no restarts, no
  kills, no writes to `~/.config/opencode` or `~/.opencode/bin`.
- **Credentials.** `opencode auth export` (read-only) into the isolated store via
  `auth import --server`. `OPENCODE_DISABLE_CHANNEL_DB=1` makes both arms use the
  same sqlite *file name* (`opencode.db`) inside their own `XDG_DATA_HOME` — v2
  otherwise derives the name from its build stamp, so a rebuilt binary would open
  a fresh database without credentials. The headless arm also sets
  `OPENCODE_SERVER_PASSWORD`; v1 leaves its server unsecured without it.
- **Pinned binaries.** The installed v2 binary was rebuilt while this measurement
  ran, so both arms run from frozen copies in `.yesmem/tmp/bin/`; `md5` and the
  version stamp are recorded in every result file.
- **Same conditions.** Same model (`gateway/gd-flash`), same prompt, same terminal
  size (50x200), same working directory — a small scratch git repo, so v2's
  shadow-git snapshot cost does not depend on repository size. A `git` role exists
  in the sampler, but in the paired series no `git` process was ever observed
  (the shadow index was already warm), so the snapshot cost is **not** separated
  out in the reported tables.
- **Paired design.** Both TUIs stay up and alternate one stream per arm, so both
  arms see the same host load. Round 0 is a warm-up (v1 builds its worker pool on
  the first stream) and is reported separately.
- **Stream end detection.** The TUI repaints whole frames, so a text marker cannot
  distinguish the current answer from a previous one. Idle output is measurably
  zero (0 bytes/2 s), so the stream window ends at quiescence (3 s without output,
  after an initial burst).
- **Detached servers.** The v1 shared server detaches (ppid 1) and outlives its
  TUI, so a later TUI may attach to it and the server is then *not* a child of the
  TUI. The sampler therefore roots at the server process and adds the TUI as the
  client role. A process counts as this arm's own only if its `XDG_DATA_HOME`
  **normalises** to the arm's data dir *and* its executable is the arm's pinned
  binary; leftover processes are terminated before a run and re-checked by start
  time immediately before each signal.
- **Host load** is recorded for every window. Absolute percentages under load are
  not portable; the paired ratios are. Note the load includes the harness's own
  two TUIs and two servers.

## Reproduce

```sh
mkdir -p .yesmem/tmp/{bin,benchdir}
cp ~/.opencode/bin/opencode   .yesmem/tmp/bin/opencode-v2
cp ~/.opencode/bin/opencode-v1-bin .yesmem/tmp/bin/opencode-v1
# isolated config + credentials: one XDG_CONFIG/DATA/STATE/CACHE_HOME per arm,
# `opencode auth export` piped into `auth import --server` against that arm's server

python3 bench/b1_paired_measure.py --rounds 7 --out .yesmem/tmp/b1-paired.json
python3 bench/b1_analyze.py .yesmem/tmp/b1-paired.json     # CPU / idle / PSS / load
```

Token normalisation needs the streams' wall-clock bounds, which only runs after
commit `f1c98c27c6` record; for an older result file pass `--last=<rounds>` and the
output is marked APPROXIMATE. For a file with wall bounds the token table is
matched 1:1 and needs no flag.

Raw result files and the terminal capture live in `.yesmem/tmp/` (git-ignored).

## Headless cross-check (CLI client instead of the TUI)

Same model, same prompt, `serve` + `run --server/--attach` as two separate
processes, 5 streams per arm (all exit 0; the first is warm-up). It exists to
separate *architecture* from *client implementation*.

| role | v2 | v1 |
| --- | --- | --- |
| client (`run` CLI) | 1.41 | 9.62 |
| server | 14.13 | 2.92 |
| worker | — | 11.91 |
| **total** | **15.90** | **24.37** |

Server-side the arms are equal here too: v2 14.13 vs v1 server+worker 14.83.

## Verdict

The premise has two halves; they come out differently.

**1. "v2 costs significantly more CPU than our v1 fork under streaming" — holds
for the TUI, not in general.** With the TUI as client: 31.12 vs 15.81 % of one
core (1.97x; series 1: 1.96x) and 1.592 vs 0.743 s per 1000 output tokens (2.14x).
With the CLI `run` as client the ranking *reverses* (v2 15.90 vs v1 24.37).
"v2 is heavier" is therefore a property of the TUI client, not of the core.

**2. "a relevant share of it sits in the server process, which B1 could move" —
does not hold.** Decomposing the TUI gap with consistent per-stream arithmetic
(median of per-stream totals; the parts are medians of per-role values and need
not sum to exactly 100 %):

| | series 2 (primary) | series 1 (replication) |
| --- | --- | --- |
| total gap | 15.32 pts | 13.69 pts |
| client (TUI) share | 14.55 pts = 95.0 % | 11.23 pts = 82.0 % |
| server-side share | 0.49 pts = 3.2 % | 1.42 pts = 10.4 % |

B1 can only touch the server side, i.e. 3-10 % of the difference. And the server
side is not where the arms diverge: v2's single server process (9.49) is 1.05x
v1's server + worker *together* (9.01) in the TUI series, and in the headless
cross-check they are equal (14.13 vs 14.83).

**Upper bound for B1.** Moving AI work out of the v2 server can relocate at most
the server's whole stream cost — 9.49 points of one core in the primary series
(14.13 headless). The AI-attributable part is bounded by what the same work costs
in v1's existing worker: 6.44 points (TUI), 11.91 (headless). Since that work
still has to run somewhere, B1 moves CPU between processes rather than removing
it; it cannot be expected to close a gap that is 82-95 % client-side.

**Go/No-Go: No-Go for B1 as a CPU lever.** The measured lever is the TUI client,
not the server. If B1's actual motivation is server event-loop responsiveness
during a stream rather than CPU totals, this measurement neither supports nor
refutes it — it was not measured.

Caveats on the premise as written: its v1-fork baseline (~3 %) is not
reproducible in this setup — the v1 fork measures 15.81 % (TUI) / 24.37 % (CLI) of
one core under streaming — so the "v2 ~40 % vs v1 ~3 %" framing overstates the
ratio by roughly 6x. Absolute load is modest throughout: even the TUI case is
~31 % of one core on a 16-core host. The most plausible source of the old ~3 %
figure is that it predates the v1 worker pool: that pool alone accounts for
6.44 points here.

## Limits

- The v2 arm runs `--standalone` (private server child) rather than the managed
  background service, because the managed-service registry is not isolatable by
  `XDG_STATE_HOME` and touching the live service was out of bounds.
- The measured symbol-level attribution of the v2 server CPU was **not** done
  (no in-process profile). The server numbers are totals per process.
- Assumed, not verified: the measured v2 binary carries the workingv2 line
  (B3/B4). The stamp says `workingv2`; the exact commit behind a compiled binary
  cannot be read back from it.
- The installed v2 binary was **rebuilt by another process at 21:01 during this
  session** (`0.0.0-yesloop-v2-port-…` → `0.0.0-workingv2-202610131858`). Both
  arms were therefore measured from frozen copies taken at 21:09. The rebuild
  cannot be attributed from this diff; what is verified is that the pinned copies
  match the installed binaries (`md5`) and that every result file records the md5.
- v1's worker pool is documented to retire after 30 s idle, and consecutive v1
  streams in the paired series are ~35-40 s apart, yet every v1 round shows
  non-zero worker CPU (5.06-7.33 %). So either the pool does not retire in TUI
  mode or a cold start sits inside the measured windows. The direction is
  conservative (it inflates v1), but the data cannot separate the two readings.
- `terminal_bytes` is recorded per stream but not analysed, so "v2 repaints more
  terminal bytes" remains an unquantified confounder for the client share.
- The headless result files predate the power-profile end sample and carry no
  `power_profile` field at all, so its absolutes are cross-run comparable only
  under the assumption that the profile stayed `performance`.
- Idle windows were sampled while the host load was 11.2-11.7 (before) and
  9.7-10.2 (after), i.e. above the 8.0-10.9 band quoted for the streaming rounds.
